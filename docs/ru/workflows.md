# Рабочие процессы

[English](../en/workflows.md) | **Русский**

Откройте **Проект → Рабочие процессы**, создайте схему, сохраните и запустите её.
У схемы должен быть ровно один начальный исполняемый узел. Циклы запрещены;
ограничение — 500 узлов и 2000 связей. Заметки не исполняются и не имеют связей.

| Узел | Поведение |
| --- | --- |
| Задача | Запускает шаблон из этого проекта с параметрами узла |
| Подтверждение | Ожидает одобрения или отклонения; по истечении заданного тайм-аута отклоняется |
| Задержка | Ожидает указанное положительное число секунд |
| Оповещение | Отправляет сообщение в Telegram проекта; результат зависит от выбранного поведения при ошибке доставки |
| Заметка | Показывает комментарий |

Связи срабатывают при успехе, ошибке либо любом результате. **Все** требует совпадения
условий всех входящих связей; **Любое** запускает узел после первого подходящего результата.
Недостижимые ветки пропускаются. В рамках запуска на одном сервере узел выполняется не более
одного раза. Ошибка задачи или отклонение подтверждения делает весь запуск неуспешным,
даже если обработчик ошибки завершился успешно. Остановка завершает активные и ожидающие
задачи, отменяет подтверждения и задержки.

Каждое сохранение создаёт неизменяемую ревизию схемы. Редактирование не меняет схему начатых
и завершённых запусков. Сами шаблоны задач остаются общими: при запуске узел получает текущую
версию шаблона. Необязательная начальная версия увеличивается для каждого запуска и передаётся
его задачам. Первая задача служит ссылкой на сборку для узлов развёртывания.

Просмотр доступен участникам проекта. Для изменения и удаления нужны права управления
ресурсами проекта; для запуска, остановки и подтверждений — права запуска задач проекта.
Дополнительные права на отдельный шаблон не дают доступа к управлению рабочим процессом.
Действия записываются в журнал аудита.

## Оповещения

Сначала настройте Telegram в **Настройки проекта → Оповещения**. В редакторе добавьте
узел **Оповещение** или включите **Оповещать о необходимости подтверждения** у узла
подтверждения. Канал использует сохранённые настройки проекта, включая глобальный токен
бота, если проект наследует его. Токены и ID чата в схему не копируются.

Сообщение — обычный текст до 3000 символов с подстановками `{{ variable.name }}`.
Выражения, команды и HTML-разметка не исполняются. Доступны:

| Переменные | Значения |
| --- | --- |
| `project.name`, `workflow.name` | Названия проекта и процесса |
| `run.id`, `run.started_by`, `run.url` | Номер запуска, инициатор и ссылка |
| `date`, `time`, `timezone` | Дата и время постановки в очередь в выбранном часовом поясе; для подтверждения — время начала ожидания |
| `source.name`, `source.status`, `source.error` | Название, результат и краткая ошибка выбранного предшественника |
| `approval.deadline` | Срок подтверждения или «Без ограничения» |

По умолчанию источник — все завершённые узлы с непосредственной входящей связью.
Можно выбрать конкретный предшествующий узел. Незавершённые и пропущенные узлы не включаются,
отсутствующие значения заменяются на `—`. Предпросмотр использует пример данных;
кнопка тестирования отправляет явно помеченное тестовое сообщение в чат проекта.

```text
Нужно подтверждение: {{ workflow.name }} #{{ run.id }}
{{ date }} {{ time }} ({{ timezone }})
Предыдущий шаг: {{ source.name }} — {{ source.status }}
Ошибка: {{ source.error }}
Подтвердить до: {{ approval.deadline }}
{{ run.url }}
```

`source.error` содержит до трёх строк с маркерами ошибок из последних 100 записей журнала,
с ограничением длины. Распознаваемые пароли, токены и учётные данные в URL маскируются.
Это фильтрация по шаблонам, а не гарантия удаления произвольных секретов из вывода команд.
Полный журнал не отправляется. Итоговое сообщение ограничено 4000 символами.

Настройте публичный URL сервера (`web_host` / `TEXEC_WEB_ROOT`), чтобы сообщения содержали
ссылку и кнопку перехода к запуску. Подтверждение выполняется в TExec с обычной проверкой
прав пользователя; кнопка Telegram лишь открывает страницу.

Очередь и готовый текст сохраняются в БД. Есть максимум три попытки доставки с паузами
10 и 20 секунд; прерванная попытка восстанавливается через минуту. Статус, число попыток
и ошибка отображаются на странице запуска. По умолчанию ошибка доставки помечается в истории,
а узел продолжает ветку успеха. Режим **Завершить шаг с ошибкой** направляет его в ветку ошибки
и делает запуск неуспешным. Ошибка оповещения о подтверждении не меняет само подтверждение.
После остановки запуска, решения по подтверждению или истечения его срока ожидающая отправка отменяется.

В обычной работе сохраняется одна запись доставки на узел и запуск. Telegram не поддерживает
идемпотентную отправку: если сервер остановится после приёма сообщения Telegram, но до записи
результата в БД, при восстановлении возможен повтор. Редактирование схемы не меняет уже
поставленные сообщения. Экспорт проекта переносит настройки, полная копия БД — также очередь и историю.

## Передача значений Ansible

Публикуйте значения через [`ansible.builtin.set_stats`](https://docs.ansible.com/projects/ansible/latest/collections/ansible/builtin/set_stats_module.html)
с `per_host: false`. TExec добавляет callback вместе с настроенным stdout callback.
Параметр `aggregate` использует правила накопления Ansible внутри задачи. Результаты
`no_log` и статистика отдельных хостов исключаются. Артефакты доступны участникам проекта
в журнале и сведениях о задаче; не передавайте через них пароли и токены.

```yaml
- ansible.builtin.set_stats:
    data:
      release_revision: "{{ revision }}"
    per_host: false
    aggregate: false
```

Следующие узлы получают значения завершённых предшественников как переменные. Вложенные
объекты объединяются, при конфликте выигрывает задача с большим ID. Явные переменные узла
имеют приоритет; обработка секретных переменных сохраняется. Значения соседних независимых
веток не передаются. Поддерживаются локальные задачи и удалённые исполнители,
включая Docker. Версии сервера и исполнителей должны совпадать. Артефакты одной задачи —
JSON-объект размером до 1 МиБ.

## Перезапуск, история и резервные копии

Подтверждения и сроки задержек хранятся в БД и восстанавливаются после перезапуска сервера.
Назначенные удалённым исполнителям задачи используют обычную сверку состояния исполнителя.
Прерванные локальные задачи, включая ещё не назначенные, останавливаются вместе с рабочим
процессом без повторного выполнения команд. Перед новым запуском проверьте частично
выполненные внешние изменения. Для управления рабочими процессами используется один сервер TExec.

Автоматическая очистка старых задач сохраняет задачи рабочих процессов. Пока существует
запуск, отдельную его задачу удалить нельзя. Шаблон, на который ссылается сохранённая ревизия,
также защищён от удаления. Рабочий процесс можно удалить после завершения или остановки
активных запусков: схемы и история запусков удаляются, обычные журналы задач сохраняются.
Экспорт и импорт проекта переносит последнюю схему и параметры узлов с заменой ссылок
на ресурсы восстановленного проекта. Для сохранения всех ревизий, запусков, подтверждений
и таймеров нужна полная резервная копия БД.
